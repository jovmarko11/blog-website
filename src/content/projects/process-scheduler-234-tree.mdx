## Idea

### One tree, two drawings

A scheduler has to answer one question over and over: which process runs next? Here the answer lives in
a balanced search tree. Processes are keyed by how long they have waited and how long they have run,
so the next one to run is always at the edge of the tree, and every insert and removal stays logarithmic.

The assignment for Algorithms and Data Structures 2 at ETF was to build that run queue as a **2-3-4 tree**
and to show that it is the same thing as a **red-black tree**. That second part is the one I found
beautiful: the two structures look nothing alike, one has fat nodes with up to three keys, the other is a
plain binary tree with coloured nodes, and yet they are one tree drawn in two ways. This write-up is about
that equivalence, and about the three operations every search tree needs: search, insert and delete.

## Architecture

### The dictionary between the two trees

A 2-3-4 tree keeps every leaf on the same level by letting nodes grow instead of letting the tree grow.
A node holds one, two or three keys (a *2-node*, *3-node* or *4-node*, named after the number of
children). A red-black tree is a binary tree where each node is red or black, no red node has a red
child, and every path from the root down to a missing child passes the same number of black nodes.

The bridge is one rule: **a black node together with its red children is one 2-3-4 node.**

</Figure>

Read in that direction, the red-black rules stop being arbitrary. *No red node has a red child* means a
cluster never has more than three keys. *Equal black heights* means every 2-3-4 leaf is on the same level,
because each black node is exactly one 2-3-4 level. And a red node is not a separate node at all: it is a
key that lives in its black parent's box.

<Figure n="02" caption="The same tree, morphed. Drag the slider: at 2-3-4 every red key slides into its black parent's box, and the boxes are one level each.">
  <TreeLab start={[70, 50, 40, 20, 30, 80, 10, 60, 90]} mode="morph" view={1} startCaption="Nine keys. Drag the slider to see them as a red-black tree and back." />
</Figure>

The project encodes this directly in the data structure. A node has three key slots, and **slot 1 is always
the black key**; slots 0 and 2 are the red ones. A 2-node uses only slot 1, a 3-node uses slot 1 and one
neighbour, and which neighbour it uses is exactly the left-or-right choice from figure 01.

<CodeBlock file="Tree.h" meta="C++" start={63} code={`

    int keyCount = 0;
    Process keys[3];
    Node* child[4] = {nullptr, nullptr, nullptr, nullptr};
    Node* parent = nullptr;
`} />

<CodeBlock file="Tree.h" meta="C++" start={136} highlight={[137, 145, 147]} code={`

`keySlotByRank` translates "the r-th smallest key" into a slot. For a 3-node it checks whether slot 0 is
occupied: if it is, the keys sit in slots 0 and 1 and the red key is on the left, otherwise they sit in
slots 1 and 2 and the red key is on the right. Colour is never stored anywhere; it falls out of the position.

## Implementation

### Search: colours don't matter

Searching a 2-3-4 node means finding the first key that is not smaller than the one you want. If it is
equal, you are done; otherwise you go down between the two keys that bracket it. In the red-black drawing
it is an ordinary binary-search-tree lookup, and the colours are ignored completely.

<Figure n="03" caption="Two searches on the same tree: 60 is found in a leaf, 35 falls between 30 and 50 and runs out of tree at the leaf [40].">

</Figure>

<CodeBlock file="Find.cpp" meta="C++" start={4} highlight={[14, 20, 25]} code={`
bool Tree::searchProcess(Process& out, int waitingTime, int executionTime) const {
    if (root == nullptr) return false;

    Process key = Process(waitingTime, executionTime);
    Node* n = root;

    while (n != nullptr) {
        int r = 0;
        while (r < n->keyCount) {
            int slot = keySlotByRank(n, r);
            if (Process::compareValues(key, n->keys[slot]) <= 0) break;
            r++;
        }

        if (r < n->keyCount) {
            int slot = keySlotByRank(n, r);
            if (Process::compareValues(key, n->keys[slot]) == 0) {
                out = n->keys[slot];
                return true;
            }
        }
        n = n->child[r];
    }
    return false;
}
`} />

Every level costs at most three comparisons, and a 2-3-4 tree with <M tex="n" /> keys has at most
<M tex="\log_2(n+1)" /> levels, so search is <M tex="O(\log n)" />.

### Insert: split on the way, grow at the root

New keys always go into a leaf. If the leaf has room, that is the whole story. If it is already a 4-node,
it has to **split**: the middle key moves up into the parent, and the two outer keys become two separate
2-nodes. In red-black terms a split is a *colour flip*: the black middle turns red (it is joining its
parent's cluster), and its two red children turn black (they are now clusters of their own).

<Figure n="04" caption="Three inserts into the left leaf. 10 and 30 fit, 25 finds the leaf full: 20 moves up, and 25 lands next to 30.">
  <TreeLab start={{ k: [40], c: [{ k: [20] }, { k: [60] }] }} ops={[["insert", 10], ["insert", 30], ["insert", 25]]} startCaption="A root with two leaves." />
</Figure>

If the parent is full too, it splits as well, and so on upward. When the root itself splits, its middle key
becomes a **new root**. That is the only way a 2-3-4 tree gets taller, and it takes every leaf down one level
at the same moment, which is why the leaves never drift apart.

<Figure n="05" caption="Inserting 55 finds a full leaf under a full root: two splits, and the tree grows by one level at the top.">
  <TreeLab start={[10, 20, 25, 30, 45, 35, 40, 50, 65]} ops={[["insert", 55]]} />
</Figure>

Notice that the left half keeps its key in **slot 1**, not slot 0. After a split both halves are 2-nodes,

### Delete: borrow, or merge

Delete is the operation where a 2-3-4 tree is much easier to think about than a red-black tree, and it is
also the part of the project that is not finished (more on that under Lessons). So this section describes
the algorithm, and the animations run my own implementation of it rather than the repository's code.

Keys can only disappear safely from leaves. If the key is in an inner node, it first swaps places with its
**in-order successor**, the smallest key in the subtree to its right, which always lives in a leaf. Then
there are three cases:

- **The leaf has a spare key.** Remove it and stop. In red-black terms a red node disappears.
- **The leaf would become empty, but a sibling has a spare key.** **Borrow**: the key that separates them
  in the parent comes down into the empty leaf, and the sibling's nearest key goes up to replace it. In
  red-black terms this is a rotation and a recolouring.
- **No sibling has a spare key.** **Merge**: the separator comes down and the empty leaf fuses with its
  sibling into one node. The parent has lost a key, and if it is now empty, the same repair repeats one
  level up.

<Figure n="06" caption="Three deletions, three cases: 20 goes from a leaf with a spare key; 50 is in the root, so its successor 60 takes its place and the empty leaf borrows from its right sibling; 70 leaves an empty leaf whose siblings have nothing to spare, so it merges.">
  <TreeLab start={[70, 50, 40, 20, 30, 80, 10, 60, 90]} ops={[["delete", 20], ["delete", 50], ["delete", 70]]} />
</Figure>

The empty node in these animations is the 2-3-4 picture of what red-black textbooks call a **double
black**: a spot that is missing one black node on its paths. Borrowing fixes it locally. Merging pushes it
one level up. When it reaches the root, it simply disappears, and so does one level of the tree:

<Figure n="07" caption="Deleting 1 from a tree of 2-nodes: the merge repeats at every level, the root loses its only key, and the tree gets one level shorter. This is the mirror image of the root split in figure 05.">
  <TreeLab start={{ k: [4], c: [{ k: [2], c: [{ k: [1] }, { k: [3] }] }, { k: [6], c: [{ k: [5] }, { k: [7] }] }] }} ops={[["delete", 1]]} />
</Figure>

Growing at the root and shrinking at the root are the only two ways the height ever changes. Everything
else rearranges keys sideways, which is why every leaf stays on the same level forever.

## Lessons

### What the two drawings taught me

- **Two views of one structure are worth more than two structures.** Red-black rules are hard to remember
  and easy to derive once you see them as 2-3-4 nodes. Every rotation and colour flip in a textbook is a
  split, a borrow or a merge in disguise.
- **Encode invariants in the layout, not in fields.** The node never stores a colour; slot 1 is black by
  definition. That removed a whole class of bugs where a stored colour and the real shape disagree.
- **Test the data structure alone, with random operations.** Checking every invariant after every one of
  thousands of random operations finds in seconds what hand-written cases never reach.
