## Idea

### What happens between Enter and the output?

I type lines like `time | tr -":" "." | wc -c > out.txt` without thinking about them. Three programs run,
text flows from one to the next, and a file appears. The final project for Object-Oriented Programming 1
at ETF was a small command-line interpreter, and I used it to answer one question: **what exactly
happens between pressing Enter and seeing the result?**

The assignment defined eleven commands (`echo`, `prompt`, `time`, `date`, `touch`, `truncate`, `rm`, `wc`,
`tr`, `head`, `batch`) and the rules for pipes and redirection. On top of that I added eight more: `history`,
`last` and `dump` for working with earlier lines, `copy`, `tail`, `unique`, `exec` for simple arithmetic, and
`help`. I also moved every special character into one `Syntax` object, which the assignment never asked
for. The goal was code that is modular and easy to follow: small classes that each do one job, and no
clever tricks.

This write-up follows that one line, `time | tr -":" "." | wc -c > out.txt`, from the keyboard to the file.

## Architecture

### Seven layers, one direction

The interpreter is a stack of layers. Each one takes the previous layer's output, turns it into
something more structured, and hands it on. None of them ever looks back.

<Figure n="01" caption='The whole trip of <code>time | tr -":" "." | wc -c &gt; out.txt</code>. On the right of each layer is the error category that only it can report. Figures 02, 03 and 05 slow down the middle of this picture.'>
  <ParseLayers />
</Figure>

- **CommandReader** reads characters from an input stream until `\n` and returns the line as a string.
- **Tokenizer** turns the string into tokens, each one a piece of text plus a flag that says whether it
  was in quotes. It is the only place that looks at single characters.
- **PipelineParser** cuts the token list at every unquoted `|`, one segment per command.
- **RedirectionParser** takes `<`, `>` and `>>` off the end of each segment.
- **CommandParser** looks the command up in the registry and lets that command's own parser read the
  rest. The output is a `ParsedPipeline`: a list of `ParsedCommand` structs.
- **StreamResolver** decides where each command reads from and writes to: the console, a file, a
  quoted string or a pipe.
- **The commands** run. Each one reads its input stream to the end and writes its output stream.

The first five layers only build data. Nothing runs until the whole line has been parsed, so a line the
parser rejects, wherever the mistake is, does nothing at all.

Every failure is an `Exception` with one of six categories (`Lexical`, `UnknownCommand`, `Syntax`,
`StreamSemantic`, `CommandSemantic`, `System`), and each category is thrown by the layers that can
actually explain it. The interpreter's main loop catches all of them in one place and prints the
message.

## Implementation

### Reading: one character at a time

The reader does not use `std::getline`. It pulls characters from an `InputStream` one by one. That is
the same interface the commands use, so the same reader works for the keyboard and for `batch`, which
reads its lines from a file:

<CodeBlock file="src/Reader/CommandReader.cpp" meta="C++" start={16} highlight={[17, 30, 31]} code={`
    while (true) {
        int ci = m_inputstream.get();

        if (m_inputstream.eof()) {
            if (m_inputstream.isConsole()) {
                m_inputstream.clear();
            }
            if (result.line.empty()) {
                result.eof = true;
            }
            break;
        }

        char ch = static_cast<char>(ci);
        if (ch == '\\r') continue;
        if (ch == '\\n') break;
`} />

A line longer than 512 characters is cut at that length and the rest of it is skipped.

### Tokenizing: five recognisers and a flag

The tokenizer is a loop over five small recognisers. At the current position, each one either
recognises something, consumes it and returns `true`, or leaves the position alone and returns `false`.
Their order is the grammar: a pipe is checked before a word, and a dash followed by a quote is checked
before a plain quote. Figure 02 runs the loop on the example line, one iteration per frame.

<Figure n="02" caption='The tokenizer on the example line. The cursor is <code>pos</code>. For each token you can see which recognisers declined and which one consumed input. Quoted tokens have a dashed border. The model behind this figure is a TypeScript copy of the C++ parser and matched it on 6000 random lines (see Results).'>

</Figure>

<CodeBlock file="src/Parser/Tokenizer.cpp" meta="C++" start={7} highlight={[8, 21, 23, 25, 27, 29]} code={`
TokenizeResult Tokenizer::tokenize(const std::string &line) const {
    checkForLexicalErrors(line);

    TokenizeResult result;

    std::size_t pos = 0;
    const std::size_t n = line.size();

    while (pos < n) {
        // preskakanje razmaka
        skipWhitespace(line, pos);
        if (pos >= n) break;

        // Pipe - poseban token ako je | van navodnika
        if (parsePipe(line, pos, result)) continue;

        if (parseRedir(line, pos, result)) continue;

        if (parseDashQuoted(line, pos, result)) continue;

        if (parseQuoted(line, pos, result)) continue;

        parseWord(line, pos, result);
    }

    return result;
}
`} />

None of the recognisers hard-codes a character. Each one asks the `Syntax` object, so the special
symbols live in one struct:

<CodeBlock file="src/Parser/Syntax.h" meta="C++" start={9} code={`
struct Syntax {
    char pipe = '|';
    char quote = '"';
    char dash = '-';
    char redirIn = '<';
    char redirOut = '>';
    std::string redirAppend = ">>";

    bool isPipe(char c) const   {   return c == pipe;   }
    bool isQuote(char c) const  {   return c == quote;  }
    bool isDash(char c) const   {   return c == dash;   }
    bool isRedir(char c) const  {    return c == redirIn || c == redirOut;  }
`} />

The most interesting recogniser is `parseDashQuoted`. `tr -":" "."` means "replace `:` with `.`", and
the `:` must not be read as part of an option. When the tokenizer sees a dash followed by a quote, it
emits **two** tokens: a plain `-` and the quoted text.

<CodeBlock file="src/Parser/Tokenizer.cpp" meta="C++" start={50} highlight={[53, 55, 68]} code={`
bool Tokenizer::parseDashQuoted(const std::string& line, size_t& pos, TokenizeResult& result) const {
    const size_t n = line.size();

    if (line[pos] == m_syn.dash && pos + 1 < n && line[pos + 1] == m_syn.quote) {
        size_t start = pos;
        result.tokens.push_back(Token{std::string(1, m_syn.dash), false});
        pos++; // preskoci -
        pos++; // preskoci "

        std::string q;

        while (pos < n && line[pos] != m_syn.quote)  q += line[pos++];


        if (pos >= n)
            throw Exception(ErrorType::Lexical, "Unterminated string literal", (int)start);

        pos++; // preskoci zavrsni quote "
        result.tokens.push_back(Token{q, true});
        return true;
    }

    return false;
}
`} />

The tokenizer does not decide what `-` means. `wc -c` produces a word `-c`, and `tr -":"` produces `-`
and `":"`. The command's own parser gives them meaning later. The tokenizer's only job is to make sure
quoted text is never split and never mistaken for an operator. After this step the quotes are gone, and
the `quoted` flag on each `Token` is the only trace of them.

### Parsing: cut, peel, dispatch

From here on nothing reads characters. The parser works on the token list in three passes, shown in
figure 03.

<Figure n="03" caption='From 11 tokens to a <code>ParsedPipeline</code>. The pipes cut the list into three segments, <code>&gt; out.txt</code> comes off the end of the last one, and each command is parsed by its own parser. At the end the whole line has been checked, and nothing has run yet.'>
  <ShellLab stage="parse" line='time | tr -":" "." | wc -c > out.txt' />
</Figure>

`PipelineParser` cuts at every unquoted `|`. A quoted `"|"` is just text. Each segment is passed to the
next two parsers right away, so the first bad segment stops the whole line:

<CodeBlock file="src/Parser/PipelineParser.cpp" meta="C++" start={11} highlight={[19, 35, 39, 41]} code={`
ParsedPipeline PipelineParser::parseTokens(const std::vector<Token>& tokens) const {
    if (tokens.empty())
        throw Exception(ErrorType::Syntax, "Empty command line");

    ParsedPipeline pl;                 // više ti ne treba pl.ok/pl.error
    std::vector<Token> segment;

    for (const auto& token : tokens) {
        if (!token.quoted && m_syn.isPipeToken(token.text)) {
            processSegment(segment, pl);
            segment.clear();
        } else {
            segment.push_back(token);
        }
    }

    processSegment(segment, pl);
    return pl;
}


// obrada jedne komande iz segmenta
void PipelineParser::processSegment(const std::vector<Token> &segment, ParsedPipeline &pl) const {
    // Prazan segment, dve cevi zaredom ili jedna na pocetku ili kraju
    if (segment.empty())
        throw Exception(ErrorType::Syntax, "Syntax error: empty command between pipes");

    // pozivanje RedirectionParsera
    auto rr = m_redirParser.extract(segment);
    // Pozivanje CommandParsera
    ParsedCommand cmd = m_cmdParser.parseTokens(rr.core);

    cmd.in = rr.in;
    cmd.out = rr.out;
    pl.commands.push_back(cmd);
}
`} />

`RedirectionParser` works **from the end** of the segment. As long as the second-to-last token is a
redirection operator, it takes the operator and the file name off. Anything that is left and still looks
like a redirection is in the wrong place:

<CodeBlock file="src/Parser/RedirectionParser.cpp" meta="C++" start={85} highlight={[95, 99, 101]} code={`
RedirectionParser::Result RedirectionParser::parseTrailingRedirs(const std::vector<Token>& segment) const {
    Result r;
    r.core = segment;

    int i = (int)r.core.size() - 1;

    while (i >= 1) {
        const Token& filenameTok = r.core[i];
        const Token& opTok = r.core[i - 1];

        if (!isRedirOp(opTok))
            break;

        ensureValidFilename(filenameTok);
        applyOneRedir(opTok, filenameTok, r);

        r.core.erase(r.core.begin() + (i - 1), r.core.begin() + (i + 1));
        i = (int)r.core.size() - 1;
    }

    return r;
}
`} />

Last, `CommandParser` finds the command's own parser in the registry. `time` uses `SimpleCommandParser`,
where every token after the name is an argument. `wc` uses `OptionCommandParser`, where a second token
starting with a dash is the option. `tr` has its own `TrCommandParser`, because its syntax
(`tr [source] -"what" ["with"]`) fits neither.

<CodeBlock file="src/Parser/CommandParser.cpp" meta="C++" start={9} highlight={[15, 18, 20]} code={`
ParsedCommand CommandParser::parseTokens(const std::vector<Token>& tokens) const {
    if (tokens.empty())
        throw Exception(ErrorType::Syntax, "Empty command");


    const std::string& name = tokens[0].text;
    const ICommandLineParser* parser = m_registry.getParser(name);

    if (!parser)
        throw Exception(ErrorType::UnknownCommand, "Unknown command: " + name);

    return parser->parseTokens(tokens);
}
`} />

### Commands are data

Every command is described by a `CommandDescriptor`: its name, its usage, its parser, a factory for the
command object, and a small `CommandTraits` struct. The traits say what kind of argument the command
takes, whether it has an option, and whether it has an input stream and an output stream at all.

<CodeBlock file="src/Factory/CommandDescriptors.cpp" meta="C++" start={335} highlight={[349, 350, 351, 364]} code={`
class WcDescriptor : public CommandDescriptor {
public:
    std::string name() const override { return "wc"; }

    std::string usage() const override { return "wc -opt [argument]"; }

    std::string description() const override {
        return "Counts words (-w) or characters (-c) in the input text.";
    }

    CommandTraits traits() const override {
        CommandTraits t;
        t.argument        = ArgumentKind::Source;
        t.argumentRequired = false;
        t.option          = OptionKind::Required;
        t.hasInputStream  = true;
        t.hasOutputStream = true;
        return t;
    }

    const ICommandLineParser& parser() const override { return m_parser; }

    std::unique_ptr<CommandBase> create(const ParsedCommand& spec,
                                        ExecContext&) const override {
        rejectExtraArguments(spec);
        return std::make_unique<WcCommand>(spec.option);
    }

private:
    OptionCommandParser m_parser;
};
`} />

The last two traits are all the engine needs to check a pipeline. A command that is not first must be
able to read, and a command that is not last must be able to write:

<CodeBlock file="src/Engine/Engine.cpp" meta="C++" start={89} highlight={[92, 97]} code={`
void Engine::validatePipelinePosition(const ParsedCommand& spec, const CommandTraits& traits,
                                      bool first, bool last) {
    // Komanda bez ulaznog toka moze stajati samo kao prva u cevovodu
    if (!first && !traits.hasInputStream)
        throw Exception(ErrorType::StreamSemantic,
            "Command " + spec.name + " cannot receive input from pipe");

    // Komanda bez izlaznog toka moze stajati samo kao poslednja u cevovodu
    if (!last && !traits.hasOutputStream)
        throw Exception(ErrorType::StreamSemantic,
            "Command " + spec.name + " cannot send output to pipe");

    if (!first && spec.in.present)
        throw Exception(ErrorType::StreamSemantic,
            "Input redirection not allowed inside pipeline");

    if (!last && spec.out.present)
        throw Exception(ErrorType::StreamSemantic,
            "Output redirection not allowed inside pipeline");
}
`} />

That gives each command a place in a pipeline without a single `if` about a specific command anywhere
in the engine. Figure 04 groups all nineteen that way.

### Running: streams all the way down

`wc` does not know whether its text comes from the keyboard, a file, a quoted string or another command.
It reads an `InputStream` until EOF and writes an `OutputStream`. Deciding which concrete streams those
are is the job of `StreamResolver`, and it follows a fixed priority:

<CodeBlock file="src/Engine/StreamResolver.cpp" meta="C++" start={54} highlight={[55, 61, 73, 88]} code={`
    // 1. Cevovod - ulaz je izlazni tok prethodne komande
    if (inputFromPipe) {
        s.in = &defaultIn;
        return;
    }

    // 2. Redirekcija ulaza iz fajla
    if (spec.in.present) {
        try {
            s.ownedIn = new FileInputStream(spec.in.filename);
        }
        catch (const std::exception& e) {
            throw Exception(ErrorType::System, spec.name + ": " + e.what());
        }
        s.in = s.ownedIn;
        return;
    }

    // 3. Argument: pod navodnicima je neposredan tekst, inace ime fajla
    if (sourceArg) {
        try {
            if (sourceArg->quoted)
                s.ownedIn = new StringInputStream(sourceArg->text);
            else
                s.ownedIn = new FileInputStream(sourceArg->text);
        }
        catch (const std::exception& e) {
            throw Exception(ErrorType::System, spec.name + ": " + e.what());
        }
        s.in = s.ownedIn;
        return;
    }

    // 4. Podrazumevano - konzola
    s.in = &defaultIn;
`} />

A pipe is the simplest class in the project. It is one object that is an `OutputStream` for the command
on its left and an `InputStream` for the command on its right, with a string in between:

<CodeBlock file="src/Pipeline/PipeStream.h" meta="C++" start={12} highlight={[12, 15, 20]} code={`
class PipeStream : public InputStream, public OutputStream {
public:
    /// OutputStream deo
    void write(const std::string& str) override     {   m_buffer += str;    }
    void write(char c) override     {   m_buffer.push_back(c);  }
    void writeLine(const std::string& str) override      {   m_buffer += str; m_buffer.push_back('\\n');     }

    /// InputStream deo
    int get() override;

    bool eof() const override   {   return m_pos >= m_buffer.size();    }
`} />

The engine asks `PipeFlowController` for one pipe between every two neighbours. Then it runs the commands
**one after another**, left to right. Each command runs to completion before the next starts, so the
pipe is simply a buffer that fills up completely and is then read from start to finish.

<CodeBlock file="src/Engine/Engine.cpp" meta="C++" start={31} highlight={[36, 51, 52, 54]} code={`
void Engine::executePipeline(const ParsedPipeline& pipeline, ExecContext& ctx) {
    const int count = static_cast<int>(pipeline.commands.size());

    // Kontroler pravi sve neophodne PipeStream-ove izmedju komandi
    PipeFlowController controller;
    const auto links = controller.buildLinks(count);

    for (int i = 0; i < count; ++i) {
        const ParsedCommand& spec = pipeline.commands[i];
        const CommandDescriptor* descriptor = m_registry.getDescriptor(spec.name);

        if (!descriptor)
            throw Exception(ErrorType::UnknownCommand, "Unknown command: " + spec.name);

        const bool first = (i == 0);
        const bool last  = (i == count - 1);

        validatePipelinePosition(spec, descriptor->traits(), first, last);

        // Podrazumevani tokovi komande zavise od njenog mesta u cevovodu
        InputStream&  defaultIn  = first ? ctx.defaultIn  : *links[i].pipeIn;
        OutputStream& defaultOut = last  ? ctx.defaultOut : *links[i].pipeOut;

        executeCommand(spec, ctx, !first, defaultIn, defaultOut);
    }
}
`} />

<Note>
Because the commands run one after another and not at the same time, these pipes cannot stream an
endless input the way a Unix pipe can. For a teaching shell this is the right trade: there are no
threads and no blocking, and the order of events in figure 05 is the whole story.
</Note>

## Lessons

### What I'd tell myself at the first commit

- **Parse everything first, run later.** Because a complete `ParsedPipeline` exists before anything
  runs, a syntax error in the third command stops the first one from running. It also made every layer testable
  on its own, which is what made the 6000-line comparison possible.
- **Describe commands with data, not with `if` chains.** The engine checks pipeline positions using two
  booleans, and the resolver picks streams using the same traits. Adding a command means adding one
  descriptor. The engine does not change.
- **Streams are the real abstraction.** Once console, file, string and pipe were all just streams, pipes
  and redirection stopped being special cases. Even `batch` works in a pipeline (`batch cmds.txt | wc -w`),
  because it runs its lines with its own output stream, and that stream can be a pipe.

<Note kind="wrong">
"Nothing runs until the whole line is checked" is true for parsing, but not for the pipeline-position
check. `validatePipelinePosition` is called inside the loop that runs the commands, so in
`batch cmds.txt | time` the batch file is executed first and only then is `time` rejected. If
`cmds.txt` creates a file, that file stays. The fix is small: check every position (and create every
command object) in one loop, and start running only in a second loop. I found this while writing this
post.
</Note>
